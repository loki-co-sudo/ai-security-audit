# ATTACK MODE — CTF Active Flag Retrieval

> ステータス: **実装済み（2026-08-26）**。§6 の受け入れチェック（AC）は実施済み・結果は
> 各項目末尾に記載。§3の設計どおり実装したが、実装中に見つかった差分は都度この文書に反映済み。
> スコープ: ATTACK MODE の CTF Flag Hunt（[CTF_FLAG_HUNT.md](CTF_FLAG_HUNT.md)）を拡張する機能。
> 既存の CTF Flag Hunt（検出のみ・送信なし）はそのまま維持し、本機能は追加のトグルとして載せる。

---

## 1. 動機とスコープ

[CTF_FLAG_HUNT.md](CTF_FLAG_HUNT.md) の CTF Flag Hunt は「既に取得済みの認可レスポンスから
フラグ形式を検出するだけ」で、対象への追加送信は一切しない。

本機能はこれを一歩進め、**LLM が偵察結果から脆弱性を判断し、実際にペイロードを送信して
検証しながらフラグを探す**、能動的なモードを追加する。対象は TryHackMe 等、ユーザーが
利用規約上テストを許可された CTF/学習プラットフォームを想定する。

### 1.1 これは `EXPLOIT_TRANSMISSION_ENABLED` の変更ではない

本ツールの根幹の安全設計 `EXPLOIT_TRANSMISSION_ENABLED = False` /
`_assert_no_transmission()`（[recon_agent.py](../agents/recon_agent.py)）は、
**通常の ATTACK MODE（バグバウンティ・実運用の対象調査）に対して一切変更しない**。

本機能は、それとは完全に独立した新しい実行パス（別モジュール・別の安全フラグ
`CTF_ACTIVE_MODE_ENABLED`）として追加する。既存の PoC 生成（Step8、ローカル生成のみ）・
既存の ATTACK MODE の挙動には一切触れない。

## 2. 安全設計（3層の防御）

CTFという正当な用途であっても、「実際に対象へ送信する」機能は事故りうる。以下の3層で
防御する。

### 2.1 層1 — スコープの厳格化（既存より厳しい既定）

- 既存の `scope_guard.in_scope()` は `allowed_targets` が空なら **常に許可**（後方互換のため）。
- 本機能はこの後方互換を採用せず、**`allowed_targets` が空なら実行そのものを拒否**する
  （`_ctf_active_scope_guard()` を新設。既存の `in_scope()` はそのまま流用しつつ、
  空リストのケースだけ本機能側で reject に上書きする）。
- THM 等は VPN 接続のたびに対象 IP が変わるため、GUI 上で「今回のセッションで許可する
  ホスト/IP」を毎回明示入力させる（前回値は残すが、空のまま実行はできない）。

### 2.2 層2 — 破壊的操作の機械的ブロック（LLM の判断だけに頼らない）

LLM に「非破壊的なものだけ選んで」と指示するだけでは事故を防げない。送信直前に、
生成されたペイロード文字列を**決定的なブロックリスト**でチェックし、該当すれば
**LLM の判断に関わらず機械的に送信を拒否**する。

```python
# core/ctf_safety.py（新設）
DESTRUCTIVE_PATTERNS = [
    # SQL: 書き込み・スキーマ破壊系（読み取り目的の SELECT/UNION は許可）
    r"(?i)\bDROP\s+TABLE\b", r"(?i)\bDELETE\s+FROM\b", r"(?i)\bTRUNCATE\b",
    r"(?i)\bUPDATE\s+\S+\s+SET\b", r"(?i)\bALTER\s+TABLE\b",
    r"(?i)\bINSERT\s+INTO\b",
    # OSコマンド: 破壊・DoS・永続化系
    r"rm\s+-rf", r"\bmkfs\b", r"\bdd\s+if=", r":\(\)\s*\{\s*:\|:&\s*\};:",  # fork bomb
    r"\bshutdown\b", r"\breboot\b", r"\bkill\s+-9\s+1\b", r">\s*/dev/(sd|nvme)",
    r"\bchmod\s+000\b", r"\buseradd\b", r"\bpasswd\b",
    # 一般: 大量データ送信・無限ループ的なペイロード（DoS化防止）
]

def is_destructive(payload: str) -> tuple[bool, str]:
    """マッチしたら (True, 理由) を返す。呼び出し側は理由付きでUIに出し、送信を拒否する。"""
```

- この関数は「実際に対象へ送信する直前」の1箇所に必ず挟む（新設する送信ラッパー
  `_send_ctf_payload()` に集約し、複数箇所にコピーしない）。
- ブロックされたペイロードは**送信されない**。UI に理由付きで表示し、LLM には
  「このアプローチは使えない、別の手を考えて」と伝えて次の候補に進む。
- HTTP メソッドは既定 GET のみ。POST/PUT/DELETE/PATCH を使う候補は、ボディのブロックリスト
  チェックに加えて「読み取り確認が目的か」を LLM 自身に一言添えさせ、ログに残す。

### 2.3 層3 — 実行中のセーフティネット（DoS化・暴走の防止）

- **総リクエスト数の上限**（`max_ctf_requests`、既定 30 — `web_fuzzer.py` の
  `max_requests` と同じ考え方）。上限に達したら Tier に関わらず停止し、
  「ここまでで見つからなかった」と正直に報告する。
- **連続エラーでの自動停止**: 直近 5 回連続で 5xx / タイムアウト / 接続エラーが
  出たら、対象が壊れかけている・落ちている可能性を疑い、それ以上の送信を止める
  （`web_fuzzer.py` の考え方を踏襲）。
- **同一オリジン限定**・**ジッター**（`WebProber`/`FuzzAgent` と同じ既存の仕組みを再利用）。
- 各送信・各レスポンスの要約を逐次ログ（`_log()`）に残し、`reports/` に保存する
  レポートにも「送信したペイロード一覧（何を試して何が起きたか）」を必ず含める
  （後から人間が監査できることを、機能の一部として必須にする）。

## 3. ペイロードの Tier 設計と段階的エスカレーション

「狭めすぎない」というひろの要望どおり、固定の短いブロックリストに絞らず、
LLM に**広い候補を考えさせつつ**、段階（Tier）ごとに区切って**軽い手から順に**試す。
各 Tier の後にフラグが見つかれば即終了。見つからなければ、非破壊の範囲で次の Tier に
進む（ユーザーが GUI で「どの Tier まで自動で上げてよいか」の上限を設定できる。既定は
Tier 2 まで。Tier 3 に進むには追加の確認ダイアログを挟む）。

| Tier | 内容（例。固定リストではなく方向性） | 破壊性 |
|---|---|---|
| **0**（既存） | 取得済み応答からの検出のみ（CTF_FLAG_HUNT.md） | 送信なし |
| **1 軽い** | 既知/推測パスの拡張巡回（`/flag.txt` 等のワードリスト）、無害なパラメータ操作（`?debug=1` 等）、コメント・ソースマップ等の深掘り | 読み取りのみ |
| **2 中程度** | 読み取り目的の LFI/パストラバーサル確認、UNION-based SQLi（`SELECT` のみ・書き込み系は層2でブロック）、SSRF の読み取り確認、非破壊コマンド限定のコマンドインジェクション確認（`id`/`whoami`/`cat`/`ls` 等） | 非破壊・読み取りのみ |
| **3 踏み込み**（既定オフ・追加確認あり） | 認証バイパス試行（JWT改ざん・セッション固定等）、デシリアライズの非破壊 PoC（情報読み取りに限定したガジェット）、blind/time-based SQLi（読み取り目的） | 非破壊だが影響範囲が広いため追加確認 |

**Tier を問わず絶対に生成・送信しない**（層2のブロックリストで機械的に弾く前提だが、
LLM への指示としても明記する）:
- データの書き込み・削除・改変（SQL の DML/DDL 書き込み系、ファイル書き込み/削除）
- ブルートフォース（大量の認証試行）・C2 の確立
- 対象の可用性を損なう操作（DoS・リソース枯渇・再起動・強制終了）
- 他ユーザーに影響する操作（アカウントロック、パスワード変更、メール送信等）

## 4. GUI/UX

- `gui/panels/attack_panel.py` に、既存の「CTF Flag Hunt」（送信なし）とは別に、
  **「CTF Active Retrieval」**チェックボックスを追加（既定オフ・赤系の色で「送信を伴う」
  ことが視覚的にわかるようにする）。
- ON にすると、既存の `allowed_targets` 設定とは別枠で「このセッションで送信を許可する
  ホスト」の入力を必須で求めるダイアログを表示（空のまま実行はできない＝層1）。
- 実行前に、送信を伴う旨・段階的にペイロードを試す旨を明記した確認ダイアログを一度挟む
  （既存の「全自動承認」の警告ダイアログと同じトーン）。
- 実行中は、各 Tier の開始・各送信・各判定結果をリアルタイムでログ表示（何を試して
  何が起きたかが常に見える状態にする。ブラックボックス化しない）。
- Tier 3 まで自動で進めるかどうかは、既定オフのチェックボックス（「深い手口まで試す」）
  で別途オプトインさせる。

## 5. 実装差分（ファイル単位・見込み）

- **`core/ctf_safety.py`（新設）**: `is_destructive()`、`_send_ctf_payload()` ラッパー
  （送信直前ブロックチェック・レート制限・連続エラー検知・ログ記録を一元化）。
- **`core/scope_guard.py`**: 変更しない。空リストを reject する判定は呼び出し側
  （`agents/recon_agent.py` の新関数）に持たせ、`in_scope()` 自体の後方互換は壊さない。
- **`agents/recon_agent.py`**: `run()` に `ctf_active: bool = False` と
  `ctf_active_targets: list[str]`、`ctf_active_max_tier: int = 2` を追加。CTF Flag Hunt
  （Step7.5）の後、フラグ未検出時のみ新フェーズ「Step 7.6: CTF Active Retrieval」を実行。
  LLM 呼び出しは既存の `_stream_llm`（STRONG）を再利用し、システムプロンプトに Tier ごとの
  方針・禁止事項（§3）を明記する。
- **`gui/panels/attack_panel.py`**: 上記 §4 の UI 追加。
- **`tools/run_selftest.py`**: `is_destructive()` の単体テスト（ブロックすべきペイロード・
  ブロックすべきでない読み取り系ペイロードの両方を網羅）、スコープ空リスト時の reject
  確認、連続エラー時の自動停止ロジックの単体テストを追加。
- **`testlab/vuln_server.py`**: Active Retrieval を試すための、意図的に脆弱なエンドポイント
  （読み取り専用の LFI・SQLi 確認用）を追加（既存のダミーフラグと組み合わせる）。

## 6. 受け入れチェック（AC・実施結果）

1. **通常 ATTACK MODE は無変更**: `ctf_active=False`（既定）で、既存の出力・動作が
   従来と完全に同一であること。→ **コードレビューで確認**（`if ctf_active and ...` の
   外側には一切変更を加えていないため、`ctf_active=False`の経路は物理的に到達不能。
   専用の回帰テストは書いていない。既存の非LLM回帰スイート62件が全てグリーンで
   間接的に裏付けている）。
2. **スコープ空なら拒否**: `ctf_active=True` かつ許可ホスト未入力 → 実行が始まらず、
   理由が UI に表示されること。→ **確認済み**（`test_ctf_active_retrieval` ⑦・
   `require_explicit_scope()` のユニットテスト、GUI側は `_update_ctf_active_hint()`/
   `_start_scan()` の早期チェックで担保）。
3. **破壊的ペイロードは機械的に拒否**: `is_destructive()` にマッチする候補は、LLM が
   提案しても実際には送信されないこと。→ **確認済み**（`test_ctf_active_retrieval` ①⑥。
   LLMがDROP TABLEを提案するケースで、実際にBLOCKEDとして送信ゼロになることを確認）。
4. **Tier の段階的エスカレーション**: `testlab/vuln_server.py` の Tier1 で見つかる
   フラグでは Tier2/3 に進まないこと。→ **確認済み**（`test_ctf_active_retrieval` ⑧。
   Tier1で発見した場合、Tier2のLLM呼び出し自体が発生しないことを確認）。
5. **暴走しない**: リクエスト数上限・連続エラー時の自動停止が実際に発動すること。
   → **確認済み**（`test_ctf_active_retrieval` ③。接続不能ポートへの連続送信で
   `max_consecutive_errors` 到達時に停止することを確認）。
6. **監査可能**: 実行後のレポートに、送信したペイロードと結果の一覧が含まれること。
   → **実装当初は漏れていた**（Step9のレポートbody組み立てにctf_active_logの配線が
   なかった。レビューで発覚し追加。`agents/recon_agent.py` の `body` 組み立てに
   `## CTF Active Retrieval — Sent Requests (audit log)` 節を追加）。GUI操作込みの
   E2E確認（実際にレポートファイルを開いて目視する）は未実施 — ロジック上は
   `recon_data["ctf_active_log"]` が `guard.format_log()` の結果で埋まり、それが
   `body` 文字列に連結されることをコードで確認。
7. **既存の安全フラグは不変**: `EXPLOIT_TRANSMISSION_ENABLED` / `_assert_no_transmission()`
   の本文に git diff で変更がないこと。→ **確認済み**（`git diff` で定義行に一致なし。
   コメント内の言及のみ追加）。
8. **回帰**: `tools/run_selftest.py`（非LLM回帰）がグリーン。→ **確認済み**（62 PASS /
   0 FAIL / 5 SKIP）。

**未実施（実機・実LLM・実THM環境）**: GUI起動での目視確認（`npm`相当のGUIアプリ起動が
必要・ヘッドレス環境のため未実施）、実LLM（STRONG/FAST）を使ったTier2/3の実走（本物の
LLMがどんな候補を提案するかは、モックしたテストでは検証できていない）、実際のTHM等の
CTFターゲットに対する実走。これらは課金・実対象への送信を伴うため、ユーザーの実施可否
確認なしに勝手に行わない。

## 7. 今回のスコープ外

- Tier 3 を超える手法（RCE の確立、シェル取得後の横展開等）は対象外。
- CTF プラットフォーム固有の VPN 接続・認証の自動化は対象外（接続はユーザーが手動で行う
  前提。対象ホストの入力のみ本機能が扱う）。
- ブロックリスト（§2.2）は初期実装後も、実際の CTF 演習で誤検知/見逃しがあれば
  継続的に見直す（固定して終わりにしない）。
