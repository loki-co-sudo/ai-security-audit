# 未使用ケース（自律調査の評価用）の作り方

作成: 2026-10-24。対象: 自律調査（`research_*`）の Stage 2〜3 評価（[AUTONOMOUS_DISCOVERY_STAGE1.md](AUTONOMOUS_DISCOVERY_STAGE1.md)）で、
開発者（れい）が**中身を知らない**ケースを用意する人向けの手順書。要求仕様の根拠は
[AUTONOMOUS_DISCOVERY_REQUIREMENTS.md](AUTONOMOUS_DISCOVERY_REQUIREMENTS.md) §3・§7.1・§7.5。

## 1. なぜ必要か

開発ケース（TeamDocs）は開発者が調整に使ったので、そこでの成功は『未知の欠陥を見つけた』証拠にならない。
システム・ケースの両方を同じ開発者が作ると、ケース側にシステムの癖が入る。**中身を知らないケースで、方式を凍結してから評価する**ために、
ケースの設計と欠陥の埋め込みを別の人（または別のモデル）が行う。れい（このシステムを作ったモデル）はケースを作らず、中身も読まない。

## 2. 調査（エージェント）が見るもの／見ないもの

| 見る（公開側） | 見ない |
|---|---|
| 案件ファイル（`testlab/lab/blind_cases/<id>.json`）: 公開仕様（操作・パス・パラメータ・アクセス条件の条項と文言・返却項目）、アカウントの権限区分と認証情報の参照名、許可ホスト、予算 | 正解ファイル（欠陥の場所・種類・根拠の有無）、被験環境のコード、トークンの値、オブジェクトID・利用者ID（起動ごとにランダム。観測でしか知れない） |

調査は、仕様の**条項**を『拒否されるべき』という期待値の独立した根拠として引用します。仕様に書いていない挙動は、逸脱を観測しても『候補』止まりで確定しません（これも測りたい性質です）。

## 3. 作るファイル（3点）

テンプレート: `testlab/lab/unseen/TEMPLATE_{case.json,truth.json,app.py}`（動く最小例。コピーして書き換える）。

1. **案件ファイル** `testlab/lab/blind_cases/<id>.json` — 形式はテンプレート参照。`"split": "holdout"` にする。仮説・検査手順・期待値・正解らしい語（脆弱・不備・欠陥・バグ・IDOR・exploit 等）は書けない（検査で弾かれる）。
2. **被験環境** `testlab/lab/unseen/<name>.py` — `testlab.lab.apps.LabApp` を継承したクラス。コンストラクタは `(canary=None, flaws=frozenset(), seed=None)`。
   `roles` に案件のアカウント名をすべて入れる（名前が `user_expired` のアカウントは常に401）。`flaws` は有効にする欠陥の名前の集合で、**空なら全操作が仕様どおりの正常な環境**になるようにする。
   IDは `seed` で決定論的に、無ければランダムに作る（起動ごとに変わる）。
3. **正解ファイル** `testlab/lab/truth/<id>.json` — `flaws`（欠陥）・`non_flaws`（正常だが紛らわしい挙動）・`unverifiable`（検証不能なはずの操作）・`env_flaws`（環境に有効にする欠陥名）・`app`（`{"module": "testlab.lab.unseen.<name>", "class": "App"}`）。
   欠陥は `{"flaw_id", "family", "op_id", "spec_grounded", "reachable"}`。`family` は `object_authz`（他人のオブジェクトに到達）／`function_authz`（権限のない機能）／`unauth_access`（未認証で到達）／`field_exposure`（仕様外の項目）／`list_scope`（一覧に見えるはずのない要素）／`other`。
   `spec_grounded=false` は『仕様に書いていないので期待値が推定になる欠陥』。`reachable=false` は調査が到達できない欠陥（GET以外が必要など）。

## 4. 仕様で使える語彙（アクセス条件 `access.kind`）

`public`（認証不要）／`authenticated`（認証済みなら誰でも）／`own_list`（呼出し者の所有または共有のものだけを返す一覧）／`owner_or_shared`（所有者と共有先のみ）／`owner_only`（所有者のみ）／
`role`（`roles: ["admin"]` のように権限区分で制限）／`unspecified`（アクセス条件の記載なし）。`returns.fields` は返却項目、`returns.object_key` はその操作の対象IDを含む項目名、`returns.identity: true` は自分のIDを返す操作。
オブジェクト型には `id_field`・`owner_field`・`shared_field`（共有先の配列）を書ける。**この語彙で表せない権限モデル（テナント分離・階層的な権限など）は、近い語彙で書き、欠陥の説明は正解ファイルの `note` に残してください**（語彙の限界も評価の一部です）。

### 4.1 調査システムが前提にしていること（満たさない案件は読込時または検査でエラーになります）

- **パスパラメータは1操作に1つまで**（`/api/teams/{team_id}/docs/{doc_id}` のような入れ子は未対応。その操作は仮説が検証器で却下され、静かに検査範囲が減るため、案件の読込で拒否します）。入れ子の構造は、パスを1つのIDにまとめる（`/api/docs/{doc_id}`）か、一覧の絞り込みで表してください。
- **自分の利用者IDを返すGET操作が1つ以上**（パラメータなし・`returns.identity: true`）。ロールと利用者IDを観測できないと、所有・共有・権限の仮説を作れません。
- **IDを持つオブジェクト型には、そのIDを観測できる一覧（`own_list`）が必要**（利用者型は `identity` で観測）。IDを観測できない操作は検査できず、欠陥があっても発見できません（調査が観測していないIDは使わない安全規則のため）。
- **クエリパラメータは未対応**（仕様のパスは固定のパスまたは `{id}` だけ。絞り込み・ページ送りのためのクエリ文字列は調査が送りません）。クエリで変わる挙動に欠陥を置く場合は『到達不能(reachable=false)』にしてください。
- 送れるのは**読取り(GET)だけ**です。副作用のある操作の欠陥や、POSTが必要な認可の不備は『到達不能(reachable=false)』または『検証不能』として扱われます。
- これらの前提は**現在の調査システムの限界**です。限界の外にある欠陥は、見つからなくても『システムが劣る』のではなく『対象外』として報告されます（その区別のため、`reachable` を正直に書いてください）。

## 5. 設計の指針（独立性と難しさ）

- **別のドメイン・別の構造にする**: TeamDocs（文書・コメント・管理者）と操作名やパスが似たものは独立と見なせません（検査で弾きます）。名前やIDだけを変えたものは不可。
- **規模の目安**: GET操作 8件以上、アカウント 4件以上（一般3＋管理者1＋期限切れ/無効1）、オブジェクト型 2種以上（所有関係が違うもの）、予算は40前後。
- **欠陥は3〜5件**。うち**調査の規則の型の外側**（`list_scope`・`other`、規則が提案しない種類）を1〜2件、**仕様に根拠のない欠陥**（`spec_grounded=false`）を1件、残りは規則の型の内側。
- **紛らわしい正常**を2件以上: 共有先が読める、管理者専用が正しく403を返す、仕様どおり公開、似た名前の操作が正しく実装されている、など。欠陥と同じ見た目の正しい実装を混ぜると、偽陽性を測れます。
- **GET以外の操作を1件以上**（調査は送らず『検証不能』として残すかを測ります）。**アクセス条件が `unspecified` の操作を1件以上**。
- **正常版（`flaws` が空）の案件ファイルも1件**: 同じ環境を欠陥なしで動かして、所見を捏造しないかを測ります（案件ID・正解ファイルを分けて、`env_flaws: []`）。
- 欠陥の例（規則の外）: 一覧に特権ロールだけ他人の要素が混ざる／別の操作に渡すIDを経由して他人のデータが見える／一覧の要素に内部IDや他人のメールが混ざる／所有者でも共有先でもない利用者に共有先の一覧が見える／ページ送りの2ページ目だけ絞り込みが外れる。

## 6. 安全上の制約（守ってください）

被験環境は 127.0.0.1 だけで動き、外部通信・ファイル書込み・実在の秘密値や個人情報を使わない。リクエストはGETのみが調査から届く設計ですが、環境側でも副作用を持たせない。実在のサービスのコードや脆弱性情報を持ち込まない。

## 6.1 作成者側のファイル（作成者のテスト・検証記録）の置き場
ケースを作る過程で書いた確認用のスクリプト・検証記録（権限・正常動作・欠陥の切り替えの確認など）は、評価の再現性を支える記録なので残してよい。ただし**正解や被験環境と同じく、調査側（調査システム・評価ランナー・開発者のれい）から隔離する**。
- 置き場所は `testlab/lab/unseen_author/<ケース名>/`（`testlab/lab/unseen/` には置かない。そこは被験環境のモジュール置き場で、調査側から読まれる場所と同じ階層）。ファイル名にも `_author_` を含める。
- 調査側のコード（`core/autonomy/research_*`）は、このディレクトリや `_author_` を含むファイルを読まない・importしない（固定試験 `ResearchBoundaryTest` が検査する）。凍結の対象（`FP_FILES`）にも入れない。
- れい（開発者）は、これらを読まない。保存・コミットは作成者側で扱う。
- 既に `testlab/lab/unseen/` に置かれた過去のケース（`cobalt_author_*`）は、移動するかは作成者側の判断に任せる。

## 7. 検査（調査は実行しません）

```bash
.venv/bin/python3 tools/research_case_check.py --case testlab/lab/blind_cases/<id>.json --truth testlab/lab/truth/<id>.json
```

形式・漏えい語・独立性（TeamDocsとの類似）・正解ファイルの整合・被験環境の起動と `roles`/`credentials()` を確認し、構造の要約（欠陥が規則の型の内側/外側の何件か等）を出します。
エラーが無くなるまで直してください（警告は設計の参考）。**調査を実行して結果を見ながら調整することは、そのケースを使用済みにします**（してはいけません）。

## 8. 渡し方と、その後の流れ

1. 案件ファイル・被験環境・正解ファイルを置き、§7の検査を通す。
2. れいに『ケースが準備できた』と伝える（ケースIDの一覧だけで十分。**中身や正解は伝えない**）。
3. れいは、評価方式・係数・予算・LLM設定を**凍結**（`docs/` に記録）してから、保留ケースとして一括評価する（`tools/research_eval.py` の `--include-holdout`）。使用記録が残り、凍結後にコードが変わっていれば評価は拒否される。
4. 結果（発見率・偽陽性・候補・未判定・費用・方式間の比較）は、ケースを**開ける前**の状態で報告される。結果を見てから案件や方式を変えたら、そのケースは使用済みとして扱う。
5. 評価後に正解を見直す場合（正解にない所見が実は正しかった等）は、旧結果と評価器の変更履歴を残して再採点する（要求仕様 §7.4）。

## 9. よくある質問

- **LLMにケースを作らせてもいい？** 可。ただし、このシステムの開発に使っているモデル（れい＝Claude）は避け、別のモデルか人が作ってください（癖が入るため）。作った後は、人が検査と目視確認をしてください。
- **ケースは何件必要？** 最低3件（欠陥ありの2件＋正常版1件）。件数が増えるほど、方式間の差を主張できます。同じ環境のID違い・繰返しは1件と数えます。
- **途中で作り直したくなったら？** 評価前なら自由。評価後に直したくなったら、そのケースは使用済みなので、別の新しいケースを作ってください。
