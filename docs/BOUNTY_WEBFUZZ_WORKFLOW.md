# WEB FUZZ バグバウンティ運用フロー

> 対象読者: 本ツールを使って合法なバグバウンティ（許可された対象範囲内でのみ活動する
> 脆弱性報告プログラム）に参加したい人。
> 前提: [BOUNTY_ROADMAP.md](BOUNTY_ROADMAP.md) の Phase A〜D（スコープガード・IDOR検出・
> バウンティ提出用Markdown出力）が実装済みであること。
> 併読: 安全境界・倫理的注意点は [ENGINEER_GUIDE.md Part 5](ENGINEER_GUIDE.md#part-5-セキュリティと法的注意) も参照。

このドキュメントは「WEB FUZZ を実際のバグバウンティプログラムで使うとしたら、具体的に
どういう手順を踏むか」を、画面上の操作単位まで落とし込んだものです。ツールが
自動でやってくれる部分と、**人間が必ず自分で確認・判断しなければならない部分**を
明確に分けて書いています。

---

## 全体の流れ

2026-09-05のコード調査で、フォーム送信先のorigin検査と認証通信の予算管理に不足を確認している。
同一origin限定・総予算という設計上の境界が全送信経路で強制されているとは扱わない。
改修前は外部action/認証リダイレクトのある対象で本フローの制限だけを頼りにせず、管理下のラボで動作確認する。
修正仕様は [実践運用計画 P0](PRACTICAL_ROADMAP.md) を参照。P0完了後にこの注意と操作手順を更新する。

```
Phase 0  プログラム参加前の準備（ツール外）
   │  Scope / Rules of Engagement を読む → 対象を書き出す
   ▼
Phase 1  ツール側の設定（⚙ 設定画面 / WEB FUZZ パネル）
   │  SCOPE設定 → 認証設定 → プロファイル・予算選択
   ▼
Phase 2  WEB FUZZ 実行
   │  クロール → 検出プローブ生成(AI) → ファジング → IDORチェック → AIトリアージ
   ▼
Phase 3  結果のトリアージ・手動検証（人間が必ず行う）
   │  重大度で絞り込み → CONFIDENCE要確認分の再検証 → 実際に手で再現
   ▼
Phase 4  レポート作成・提出
      📝 MD出力 → 手動検証の内容で補強 → 重複報告チェック → プラットフォームへ提出
```

---

## Phase 0. プログラム参加前の準備（ツールの外で行うこと）

ツールを起動する前に、必ず次を確認してください。ここを飛ばすと、Phase 1 の
スコープ設定を正しく書けません。

1. **対象プログラムの Scope（対象範囲）ページを読む**（HackerOne の `policy` タブ、
   Bugcrowd の `brief` など）。
   - 「対象（in scope）」のドメイン・IPレンジ・サブドメインワイルドカードを書き出す
   - 「対象外（out of scope）」も同様に書き出す（本ツールの `allowed_targets` は
     許可リスト方式のみで、除外リストには対応していません。§Phase 1参照）
2. **Rules of Engagement（行動規範）を読む**。特に次の項目を確認する:
   - リクエストレート上限（"no more than N requests/sec" のような記載があるか）
   - 複数アカウントでのテストが許可されているか（IDOR検証で第2アカウントを使う場合に必須）
   - 自動化ツールの使用可否・除外されるテスト手法（DoS系・ソーシャルエンジニアリング等）
3. **VDP（報奨金なしの脆弱性報告制度）から始める**ことを推奨します。報奨金付き
   プログラムより先に、Scope の読み方・レポートの書き方に慣れてください。

## Phase 1. ツール側の設定

### 1-1. SCOPE 設定（⚙ 設定画面）

⚙ ボタンから設定画面を開き、**SCOPE（対象範囲・バグバウンティ対応）** セクションを
開きます。

| 項目 | 入力内容 |
|---|---|
| ALLOWED | Phase 0 で書き出した対象を1行1ルールで入力（例: `example.com` / `*.example.com` / `203.0.113.0/24`） |
| MODE | `warn`（範囲外でも警告のみで続行）か `block`（範囲外は実行ブロック）。初めてのプログラムでは `block` を推奨 |

> ⚠ **`ALLOWED` を空欄のままにしないでください。** 空欄は「全対象が許可扱い」という
> 既存インストールとの後方互換のための挙動であり、バグバウンティでは対象範囲外への
> アクセスがそのまま規約違反・法的リスクになります。設定画面にも常時警告が表示されます。

`allowed_targets` は許可リスト（アローリスト）方式のみに対応しており、「全体は対象だが
特定のサブドメインは対象外」のような除外表現はできません（v1の既知の制約）。対象外の
資産がある場合は、許可リストに個別のホスト名を列挙する運用で回避してください。

### 1-2. 認証設定（WEB FUZZ パネル）

対象アプリにログインが必要な場合、パネル上部の **🔐 認証** ボタンから設定します。

- **Cookie**: ブラウザの開発者ツールから取得したセッションCookieをそのまま貼り付け
- **ヘッダー**: `Authorization: Bearer ...` のようなAPIトークン形式
- **ログインフォーム**: フォームのURL・ユーザー名/パスワードを入力（CSRFトークンは自動抽出）

**IDOR（アクセス制御不備）を検証したい場合**は、加えて **🔐 認証B（IDOR比較・任意）**
ボタンから、2つ目のアカウント（別権限のテストユーザー）の認証情報を設定してください。
ボタン脇に「複数アカウント使用は対象プログラムの規約(ROE)で許可されているか要確認」と
表示されます。**Phase 0 で確認済みでなければ、ここで一度立ち止まって確認してください。**

### 1-3. プロファイル・予算の選択

| 設定項目 | 推奨値 | 理由 |
|---|---|---|
| PROFILE | `bounty` | 「検知回避」目的の `stealth` とは思想が異なり、「対象インフラへの配慮（レート制限順守）」を目的としたプロファイル。Phase 0 で確認したレート制限を大きく超えないよう、リクエスト間隔・並列数が抑えめに設定されている |
| REQ BUDGET | プログラムのレート制限に応じて調整 | 総リクエスト数の上限。デフォルトの選択肢（80/200/400/800）はあくまで目安 — Phase 0 で確認した上限が厳しい場合は、`80` から始めて様子を見る |
| EFFORT（⚙ 設定画面） | `品質`（quality） | STRONGモデルによる検証パス（誤検知の削減、`CONFIDENCE: ENSEMBLE_MINORITY` タグ付けによる少数意見の可視化）が有効になる。提出前の精度が重要なため推奨 |

> レート制限値をプログラムごとに自動反映する仕組みは未実装です（[BOUNTY_ROADMAP.md §7](BOUNTY_ROADMAP.md)
> 将来検討）。現時点では REQ BUDGET を手動で調整してください。

## Phase 2. WEB FUZZ 実行

対象URLを入力して START すると、次の順で自動的に進みます。

1. **クロール**: 同一オリジンを浅く辿り、URL・フォームからパラメータ（注入点）を抽出する。
   `text/html` 以外（JSON API・ファイル配信系エンドポイント等）を返すページの
   パラメータも対象に含まれる。
2. **検出プローブ生成（AI・FASTモデル）**: 抽出したパラメータに対する検出用ペイロードを生成
3. **ファジング（検出のみ）**: SQLi・XSS・パストラバーサル・SSTI のペイロードを送信し、
   レスポンス異常（反射・DBエラー署名・テンプレ評価・既知ファイル署名）を観測する。
   書き込み系のエクスプロイト（データ改変・RCE実行等）は一切行わない
4. **認可チェック（第2アカウント設定時のみ）**: セッションA/Bで同一URLへのGETを比較し、
   IDORの兆候を観測する（GET等の非破壊メソッドに限定。この限定は原則であり、
   サーバ側実装次第では100%の安全性を保証するものではない）
5. **AIトリアージ（STRONGモデル）**: 観測結果を精査し、重大度（CRITICAL/HIGH/MEDIUM/LOW）・
   説明・修正案を付与してレポート化。品質エフォート時は検証パス（敵対的レビュー）も実施

進行中は右ペインにストリーミングでAIの出力が表示されます。STOPボタンでいつでも中断できます。

## Phase 3. 結果のトリアージ・手動検証

**ここが最も重要な工程です。** 本ツールは「検出のみ」であり、AIが指摘した所見は
「その可能性がある兆候」であって「確定した脆弱性」ではありません。提出前に必ず
人間が検証してください。

1. **重大度で絞り込む**: CRITICAL/HIGH から優先的に確認する
2. **`CONFIDENCE: ENSEMBLE_MINORITY` タグの所見に注意する**: 品質エフォート時、
   検証パスを複数回走らせた際に意見が割れた所見にはこのタグが付く。誤検知の可能性が
   相対的に高いため、他の所見よりも慎重に再現確認する
3. **実際に手で再現する**: Burp Suite の Repeater や curl で、ツールが示した
   URL・パラメータ・ペイロードを実際に送信し、影響（Impact）を自分の目で確認する。
   IDORの場合は、実際に別アカウントの画面から意図しないデータが見えるかを確認する
4. **影響範囲を評価する**: 「反射された」「エラーメッセージが変わった」だけでは
   報奨金プログラムでは不十分な場合が多い。実際に何が奪える／改ざんできるかを言語化する

## Phase 4. レポート作成・提出

1. パネルの **📝 MD** ボタンでバウンティ提出用Markdownを出力する
   （Summary / Steps to Reproduce / Impact / Suggested Fix の4項目）
2. **Steps to Reproduce は、Phase 3 で自分の手で再現した手順に書き換える。**
   AIが生成した手順をそのまま貼らない（AIの手順は「検出時にツールが送ったリクエスト」
   であり、第三者が再現しやすい形に整理されているとは限らない）
3. **重複報告チェックを手動で行う**: 同じ脆弱性が既に報告済みでないか、
   HackerOne Hacktivity や Bugcrowd の該当プログラムの既知課題一覧を確認する
   （本ツールはプラットフォームAPIと連携しておらず、重複チェック機能を持たない。
   [BOUNTY_ROADMAP.md §7](BOUNTY_ROADMAP.md) で意図的に対象外としている）
4. プラットフォーム上のフォームから提出する

## やってはいけないこと（まとめ）

- `ALLOWED` を空欄のまま、対象範囲を意識せずにスキャンを開始する
- Rules of Engagement を確認せずに第2アカウント（🔐 認証B）を使う
- AIの所見をそのまま「脆弱性が見つかりました」として提出する（Phase 3 の手動検証を省く）
- プログラムのレート制限を確認せずに REQ BUDGET を最大値のまま使う
- crt.sh 等で発見したサブドメイン（ATTACK MODE 側の機能）を、生存確認・所有確認なしに
  そのままテスト対象へ含める

## 練習してから使いたい場合

いきなり実際のプログラムで試す前に、同梱の `testlab/`（意図的に脆弱なローカルサーバ、
`127.0.0.1` のみにバインド）で操作に慣れることを推奨します。

```bash
python testlab/vuln_server.py          # http://127.0.0.1:8000 で起動
```

別ターミナルで本体を起動し、WEB FUZZ のターゲットに `http://127.0.0.1:8000` を指定すると、
SQLi・XSS・SSTI・パストラバーサルの検出を安全に一通り試せます（詳細は
[testlab/README.md](../testlab/README.md)）。IDOR（第2アカウント比較）の練習には対応して
いないため、IDOR機能の動作確認は本ドキュメント Phase 1-2 の設定を実際のテスト対象
（自分で用意した検証環境等）で行ってください。
