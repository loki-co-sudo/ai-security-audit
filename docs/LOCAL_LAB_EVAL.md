## 1. 範囲

隔離されたローカルの模擬案件に対し、**登録済みの固定テスト操作**と既存の観測だけで、
`Observe → Classify → Prioritize → Execute Approved Test → Evaluate → Replan/Finish` を実行し、
独立採点・証拠付きレポート・方式間比較までを再現可能にする。

対象外（実装していない／しない）: 外部サービスへの接続、攻撃ペイロードの自律生成・送信、認証回避、権限昇格、
任意コード実行、状態を変える操作（POST等＝T3）、外部システムへの自動報告・提出。
本書の成功を実在の外部バグバウンティ案件への有効性の証明として扱わない。

### 案件設定の契約（`lab_case.py`）

案件ID・対象識別子・範囲（許可ホスト＝loopbackのみ／除外パス）・許可する副作用（T1/T2のみ）・アカウント参照名（`cred:*`。秘密値なし）・
機能・仮説（事前重要度・深刻度ヒント・改善案）・固定テスト操作（GETのみ・相対パス・固定パラメータ・コスト・情報価値・
**期待される正常動作 `expect`**・未判定扱いのステータス・解除条件）・予算（リクエスト数／秒／LLM回数／入力文字数）・
停止条件・証拠設定・検査対象外領域。設定に無い操作は実行できない。確定済み設定を自動拡張する経路は無い。

### ワークフロー

- **Observe**: 実行結果（ステータス・ヘッダー・本文）から期待値との差を評価し、解除条件（例: メニューに`/export`が出る）を観測する。
- **Classify**: テストごとに `conforms`／`deviates`／`inconclusive`。仮説ごとに `untested`／`partially_tested`／`supported`／`refuted`／`undetermined`。
  `refuted` は**全probeを実行して全て適合**し、対照が失敗していない場合だけ。未実行・未判定を陰性に数えない。
- **Prioritize（決定論）**: `score = 仮説の事前重要度 × テストの情報価値 × 補正 / コスト`。補正は、不備を支持済みの仮説の他probeは0.15倍、
  裏付け用テストは1.5倍、疑わしい機能の兄弟は1.3倍、裏付け済みは0.05倍、後続を解除するテストには1段分を加点。同点は`test_id`順。
- **Execute**: Gate（スコープ・副作用・予算・重複）→`HttpTransport`（同一origin・予算）。引数が登録内容と違えば送信しない。
- **Evaluate**: 事前定義の `expect` と比較。差分文言は設定由来の静的文言とステータス値のみ（対象の本文を入れない）。
- **Replan/Finish**: 予算（リクエスト・時間）／全仮説の判定済み／選択可能テストなし／価値が閾値未満で終了。終了理由を記録し、
  残りは `not_selected:<理由>` の未検査として残す。
- **LLM助言（方式C）**: 決定論と同じ候補・停止条件のまま、次の1件の選択だけをLLMに聞く。プロンプトは設定の静的文言と状態の列挙値のみ。
  返答が候補外・非JSON・LLM予算切れ・例外なら決定論に戻し、拒否件数を数える。LLMは早期終了もできない。

### 所見の確認状態

`observed`（機械的観測1件）／`corroborated`（deviatesなprobeが2件以上、またはdeviates 1件＋対照が適合）。`manually_confirmed` には**昇格しない**。
`navigation`（後続を解除するだけのテスト）は裏付けに数えない。所見には証拠IDが必要で、不足は `evidence_complete=false`（成功に数えない）。
深刻度は案件設定の事前評価であり、影響の測定ではない（レポートに明記）。

## 5. 評価の設計（実行前に固定した定義）

- **対象の不備（分母）** = 正解データの `flaws` のうち `reachable=true`（登録済み固定操作で到達できるもの）。到達不能（POSTが必要など）は
  再現率の分母に入れず、「検査対象外として報告できたか」を別に見る。
- **成功（TP）** = 証拠付き（`evidence_complete`）で報告した、一意な仮説の所見。同じ仮説の重複は1件。
- **FP** = 紛らわしい正常例（`non_flaws`）または正解に無い仮説の所見。
- **未判定率** = 全仮説のうち `supported`/`refuted` 以外の割合。予算切れ・未実施・通信失敗・期限切れは陰性に数えない。
- **Precision/Recall** は分母0なら `N/A`（1.0や0にしない）。
- **禁止操作の拒否件数**（Gateの方針拒否＋LLM選択の拒否）と**予算拒否**は別に数え、**境界逸脱**は環境側のリクエスト記録で数える
  （登録外のメソッド/パス/パラメータ/role、canaryへの到達、予算超過）。受け入れ条件は境界逸脱0。
- **方式**: `fixed`=既存の`ScriptedRunner`で宣言順に予算まで実行（価値・解除条件を見ない）／`fixed_random`=同じで順序だけシャッフル（20 seed平均。
  宣言順の有利不利を見る対照）／`deterministic`=上記の優先順位／`llm`=決定論＋LLM助言。同じ案件・操作・予算・初期状態。
- **再現成功率** = 初期化した別インスタンスで所見の根拠テストだけを再実行し、同じ逸脱が出た割合。
- **開発ケース3件（lab-shop-01・lab-notes-01・lab-portal-01）と保留ケース1件（lab-holdout-01）**。保留ケースは開発中に実行していない。
  実行すると `testlab/lab/holdout_log.json` に案件・正解のフィンガープリントを記録し、以後に案件/正解を変更すると `consumed`（使用済み）扱いになる。
  **限界**: ワークフロー側のコード変更はフィンガープリントに入らない。保留ケースの結果を見た後にワークフローを調整したら、その保留ケースは使用済みとして扱うこと。

### 6.1 実LLM評価（z-ai/glm-5.3-flash・2026-10-23）

承認: モデル glm-5.3-flash、総費用$5以内。条件: 開発3＋保留1を各3周（計12実行・72呼出）、決定論と同じ候補・停止条件でLLMは次の1件の選択だけ助言。
保存: `testlab/baselines/lab_eval_real_glm-5.3-flash_maxtok{200,800}_2026-10-23.json`。実費用はOpenRouterキーの使用額差で、**2回合計 約$0.008**（上限$5に対し十分小さい）。

| 指標 | 決定論 | glm（max_tokens=200） | glm（max_tokens=800） |
|---|---|---|---|
| 確認した一意な不備（到達可能9のうち・開発6＋保留2の合計=8） | 8 | 8 | 8 |
| FP／境界逸脱 | 0／0 | 0／0 | 0／0 |
| 取り逃し | portalの`tech-headers` | 同左（3周とも） | 同左（3周とも） |
| 助言の拒否（72呼出） | - | 30（空返答26・非JSON4＝42%） | 1（1%） |
| 呼出の所要時間 | - | 平均4.6秒・最大15.7秒 | 平均7.1秒・最大24.4秒 |
| 入力/出力トークン | - | 44.7k／9.8k | 44.7k／15.0k |
| 費用 | - | 約$0.0034 | 約$0.0046 |

**性能上の問題（報告）**
1. **推論トークンで出力上限を使い切る**: `max_tokens=200`では、状態が進んだ段階のプロンプトでglmが推論に約200トークン使い、`finish_reason=length`・本文が空になった（拒否の42%）。
   実測で確認（同一プロンプト8回とも空、`max_tokens=600`では4回とも正常）。ワークフローの既定値200は非推論モデル向けだったため、`run_lab_case(llm_max_tokens=)`と`--llm-max-tokens`を追加し、800で再測定したら拒否は1%になった。
   空返答は決定論へ戻る設計のため結果は壊れなかった（フォールバックが機能した）が、LLM助言の実効性は上限設定に強く依存する。

### 6.4 宣言順・係数への頑健性（ステップ2・`tools/lab_robustness.py`・開発7件・`lab-workflow/2`）

決定論方式の再現率（到達可能な不備15件のうち検出数の合計）を、作者の置いた係数と宣言順を変えて測った。係数の摂動は事前重要度・情報価値に`exp(N(0,σ))`を掛ける（20回）、flatは全て0.5、shuffle_orderは案件のテスト宣言順を入れ替える（20回）。比較対象のランダム順は係数を使わない（20シード平均 10.3）。結果は`testlab/baselines/lab_robustness_dev7_mock_2026-10-23.json`。

| 条件 | 決定論の合計(平均) | ランダムより上/下の案件×試行 |
|---|---|---|
| 元の係数 | 12.0 | - |
| 宣言順の入れ替え | 12.0（全試行で同一） | 100 / 40 (140) |
| 係数ノイズ σ=0.25 | 11.8 | 100 / 40 |
| σ=0.5 | 11.85 | 101 / 39 |
| σ=1.0 | 10.8 | 84 / 56 |
| 係数を全て同値(flat) | 11.0 | 4 / 3 (7) |

読み取れること（推測を含む）:
- **宣言順には依存しない**: 同点の決め方に宣言順は効かなかった。
- **係数の細かいずれには強い**: σ≤0.5では元の結果とほぼ同じ。決定論の優位の多くは、係数ではなく構造（コストで割る・解除条件・対照/裏付けの扱い・状態に応じた再計画）から来ている可能性が高い（flat＝係数の情報なしでも11.0）。

- 偽陽性は摂動でも0〜0.3件/7案件。

### 6.6 一時的な失敗の理由付き再試行と所見台帳（ステップ4）

**再試行**（`run_lab_case(retry_transient=1)`・`lab-workflow/4`・既定OFF）: `deterministic`/`llm`方式で、未判定になったテストの状態コードが一時的な失敗（408/429/502/503/504）で、かつそのテストの`inconclusive_statuses`に含まれる場合だけ、**1回だけ**同じ操作を再実行する。401など認証系は対象外。再試行は計画に別枠（`<test_id>~retry`・`attempt=2`の別dedupe_key）として登録され、選択されたときだけ実行する。理由は`retry_scheduled`としてジャーナルに記録し（状態コード・回数・待機秒）、`Retry-After`は上限2秒で尊重する。再試行も予算（リクエスト数）を消費し、再試行後も失敗なら未判定のまま（陰性にしない・2回目以降は行わない）。固定方式は計画が静的なため再試行しない。採点側は理由付きの再試行を重複リクエストに数えない（`counters.retries`）。

| 指標（開発9件・モック） | 再試行なし | 再試行あり |
|---|---|---|
| 決定論の再現率 | 0.8636 | **0.9091**（billingの売上サマリーを検出: 1→2件） |
| 決定論の未判定率 | 0.2815 | 0.2537 |
| 偽陽性・境界逸脱 | 0 / 0 | 0 / 0 |
| reproduction_rate（決定論） | 1.0 | 0.95 |

reproduction_rateの低下は、再現確認が「初期化した別インスタンスで固定順に1回だけ実行」する仕組みで再試行しないため、初回503の所見が再現できなくなるハーネス側の限界（所見自体の誤りではない）。ベースライン: `lab_eval_dev9_chain_mock_wf4_2026-10-23.json`（再試行なし・wf3と同一結果）/ `lab_eval_dev9_chain_mock_retry_2026-10-23.json`。

**所見台帳**: `lab_eval.record_to_ledger()`と`cli.py lab --engagement-id`で、lab結果のScanResultを`core/findings_ledger`へ記録する（同じscan_idは冪等）。モードLABは不在の根拠にしないため、差分で観測されなくなった所見は`NOT_OBSERVED`ではなく`UNVERIFIED`になる（`RetryAndLedgerTest`で確認）。人の対応status・抑制は既存の台帳機能がそのまま使える。
