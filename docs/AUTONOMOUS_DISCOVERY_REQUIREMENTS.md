# 自律型脆弱性発見エージェントの要求仕様

作成: 2026-10-23（プロダクトオーナー指示）。文書の役割: **目指す技術的到達点を定義する要求仕様**。
現在の実装状況・進捗・評価結果は本書に書かない（現状との差と実現計画は
[AUTONOMOUS_DISCOVERY_STAGE1.md](AUTONOMOUS_DISCOVERY_STAGE1.md)、自律化基盤の実装進捗は
[AUTONOMOUS_IMPLEMENTATION_PLAN.md](AUTONOMOUS_IMPLEMENTATION_PLAN.md)、ローカル模擬案件の評価記録は
[LOCAL_LAB_EVAL.md](LOCAL_LAB_EVAL.md) を正とする）。要求を変える場合は、日付と理由を本書に追記する。

## 1. 位置付け

従来の「案件調査を支援する使いやすいツール」から、**自律的な発見能力の実現・実証を中心**に優先順位を更新する。
全面的な作り直しの指示ではない。既存の実装・作業中の変更・検証記録は保持する。

## 2. 最終目標

AIエージェントが、人間による調査手順の逐次指示を必要とせず、対象システムを理解し、仮説を立案し、検証計画を構成し、
観測結果に応じて調査を更新して、脆弱性を発見できるシステムを開発する。

最大の成果は作業効率化や学習支援ではなく、「自ら開発したAIシステムが、自律的な研究判断によって脆弱性を発見した」
という、**客観的に検証可能な技術的実績**を作ること。将来は許可されたバグバウンティプログラムでの活用を目指すが、
外部システムへの自律的な能動調査は初期の完成条件にしない。まず隔離されたローカル環境で能力を実証する。

## 3. 「未知」の意味と成果の主張範囲

1. **エージェントに未提示の、意図的に埋め込まれた欠陥** — 初見ケースへの適応と自律発見能力を評価する段階。
2. **評価対象の開発者・評価設計者も想定していなかった欠陥** — 想定外の問題を発見した実績。独立した確認が必要。
3. **実在ソフトウェアの未報告・未修正の欠陥** — 現実の新規脆弱性発見の実績。許可された調査と、既知情報・影響・再現性の別途確認が必要。

初見の模擬案件で成功したことを、そのまま新規脆弱性やゼロデイの発見と呼ばない。
**初期の達成目標は1**。その先に2、将来的な目標として3。各成果について、どの段階を実証したかを明記する。

## 4. 完成形に必要な能力

### A. Target Understanding — 対象理解
対象をURLの集合ではなく、機能・データ・権限の関係として整理する。エンドポイント・入力・出力・機能の対応／認証ロールと権限の関係／
データオブジェクトの所有・参照関係／API仕様・提供されたソースコード・観測結果の対応／**確認済み事実と推定情報の区別**／不明点と未調査領域の保持。

### B. Hypothesis Generation — 仮説生成
事前登録された脆弱性候補を選ぶだけでなく、観測から検証可能な仮説を生成する。仮説には次を含める:
何が問題である可能性があるか／根拠となる観測と出典／成立に必要な前提／未確認の前提／支持する観測の予測／反証条件／必要な追加観測。
もっともらしい説明だけを、発見や確認済み所見として扱わない。

### C. Experiment Design — 実験設計
仮説に対して、登録済みの安全な操作部品を組み合わせ、検証計画を作成する: 検査対象・ロール・入力・操作順の選択／正常系の対照／
期待結果と判定条件／必要な証拠／実行予算と停止条件／判定不能となる条件。

人間が仮説・対照・期待値を全部用意し、AIがtest_idを選ぶだけの方式は**実行基盤の検証**であり、自律的な仮説生成・実験設計の実証とは扱わない。
一方で、自由な攻撃コード・任意コマンド・無制限のペイロード生成は要求しない。操作部品と引数の範囲は決定論的に制限する。

### D. Research Planning — 調査計画と再計画
初期情報から調査対象と優先順位を決める／観測に応じて次の調査内容を変える／仮説を更新・棄却する／情報価値・残予算・確認完了までのコストを考慮する／
重複操作と根拠のない反復を避ける／検証不能な仮説を無理に確定しない。
対応する承認済み操作がない場合は「現在の能力では検証不能」として必要な能力と理由を残す。

### E. Evidence Evaluation / Finding Validation — 根拠の評価
次の状態を区別する: 逸脱を観測した／仮説を支持する候補が得られた／必要な対照・反証・再現確認を実施した／根拠付き所見として成立した／
必要な証拠を保存できた／保存物の整合性を確認できた／人間が確認した。

LLMの判断をそのまま脆弱性の確定判定にしない。**エージェント自身が生成した期待値との不一致だけでも確定しない**。
「この操作は拒否されるべき」等の前提を、提供仕様・所有関係・権限設定などの独立した根拠に結び付ける。仕様上の根拠が不明なら、その不確実性を残す。

### F. Autonomous Execution Lifecycle — 実行管理
時間・リクエスト・LLM予算の管理／実行履歴の永続化／中断・再開／結果不明の操作の扱い／安全な再試行／
調査完了・情報不足・予算枯渇・ポリシー制限による終了／必要な場合だけ人間へ問い合わせる。
初期設定や実行範囲の承認と、調査手順への人間の介入は別々に記録する。

### G. Autonomous Reporting — 報告
人間が根拠を追跡できる編集可能なドラフトを生成する: 問題の概要と前提条件／対象機能と影響の根拠／期待動作と観測結果／許可された操作による再現手順／
対照・反証・再現確認の結果／証拠参照と保存状態／未確認事項・棄却した仮説・未調査範囲／終了理由と予算／人間のレビュー状態。
初期段階では機械可読の実行記録とMarkdownでよい。GUIの見栄えや出力形式の追加を、研究能力の実装より優先しない。

## 5. 自律性と実行権限の分離

LLMは調査上の判断を**提案**する。実行できる操作と予算は、決定論的なPolicy Gateが強制する。

- LLMが対象や規約を解釈しただけで権限を付与しない
- 観測したリンクや新しい対象を暗黙にスコープへ追加しない
- 対象の応答・文書に含まれる指示で実行権限を変更しない
- 人間の承認を既存の禁止操作を迂回する仕組みにしない
- 本要求を根拠に、CTF能動機能を自律ループへ公開しない
- 実行不能・許可不足は理由を残して停止または別の調査へ移る

既存のセキュリティポリシーと衝突する場合は、該当箇所・影響・選択肢を示す。勝手に権限を拡張したり、目標を縮小したりしない。

## 6. アーキテクチャの方針

論理的に必要な責務: Target Model / Observation Store / Hypothesis Engine / Research Planner / Experiment Planner / Policy Gate /
Execution Runner / Evidence Evaluator / Finding Validator / Research Memory / Report Generator。

ただし**責務ごとに新しいエージェント・サービス・DBを作る必要はない**。既存のRunner・Policy Gate・Journal・RunStore・EvidenceStore・
Finding・Coverage・所見台帳を可能な限り再利用する。追加する部品は、既存部品では何が不足するかを説明する。
汎用グラフ基盤・並列Worker・複雑な長期記憶基盤は、必要性を実証してから導入する。

Research Memoryは、まずRun/案件内の観測・仮説・失敗・未解決事項の保持で成立させる。案件をまたぐ経験の再利用は、
評価ケースや正解の漏入を防げる設計にしてから追加する。

## 7. 評価設計

### 7.1 評価環境
許可された隔離ローカル環境を使う／開発ケースと未使用評価ケースを分ける／正解・脆弱性ラベル・解法をエージェントへ渡さない／
調査中に採点結果をフィードバックしない／正常系と紛らわしい正常ケースを含める／成功例だけでなく失敗例も保存する／
対象・コード・プロンプト・操作カタログ・予算・seed・評価器の版を記録する。
通常の仕様資料は入力にできるが、欠陥の場所や検査手順を教える資料を通常仕様と混同しない。
エージェントにソースコードを与えるか、ブラックボックスで調べるかも評価条件として固定する。

### 7.2 比較条件
固定的な探索、決定論的探索、LLM自律探索を比較する: 同じ対象情報／同じ操作部品／HTTP予算を揃える／壁時計時間・LLM費用・失敗率も記録／
方式ごとに有利な対象や操作を追加しない。「LLM方式だけが発見した」ことと「仮説形成や再計画が発見に寄与した」ことを区別する。
必要に応じて、初期計画を更新しない方式／観測後に再計画する方式／仮説生成を固定した方式、のような要素除去比較を行う。
全組合せを最初から実装する必要はなく、検証したい主張に必要な最小比較を選ぶ。

### 7.3 記録する研究判断
次のつながりを監査可能にする:
観測 → 仮説 → **実験前に記録した予測・反証条件** → 検証計画 → Gate判断 → 操作 → 結果 → 仮説・計画の変更。
結果を見た後の説明だけでは、実験設計能力の証明にしない。

### 7.4 指標
少なくとも次を定義する: 未使用ケースでの発見率／根拠付き所見の適合率・再現率／偽陽性・候補・未判定の件数／有効な仮説の生成率／
仮説から根拠付き所見への到達率／対照・反証の実施率／証拠充足率／発見までの操作数・時間・費用／人間の調査介入なしで完了した割合／
固定的手法に対する追加発見とその条件。

「有効な仮説」の定義を事前に決める。もっともらしい文章の数を指標にしない。各指標の分母・重複の扱い・証拠不足・未判定・評価不能を明記する。
正解にない所見は直ちに誤検知とせず、独立した確認待ちとして区別する。確認後に採点を更新する場合は、旧結果と評価器の変更履歴を残す。

### 7.5 過適合の防止
既知の開発ケースで調整する／方式・予算・判定条件・採用基準を凍結してから未使用ケースを評価する／結果を見た評価ケースは調整後の独立評価に再利用しない／
IDや名称だけ変えたケースを独立した未知ケースと扱わない／同じ案件の反復を独立した多数の案件として数えない／評価時の案件横断メモリの持越し条件を固定する。

## 8. 段階的な到達目標

- **Stage 1: 狭い領域で自律調査ループを成立させる。** 少数の機能・ロール・オブジェクトを持つ隔離アプリを対象に、人間が仮説・実験手順を逐次与えずに、
  対象観測・仮説生成・対照設計・実行・評価・再計画・報告まで通す。少なくとも次を含む固定試験を設ける:
  観測によって次の操作が変わる／誤った仮説を棄却する／対照不足を未確認のまま残す／正常な対象で脆弱性を捏造しない／
  検証能力不足や予算枯渇で理由付き終了する／実行履歴から判断と証拠を追跡できる。
- **Stage 2: 未使用ケースへの適応。** 凍結した方式で複数の未使用案件を評価し、初見の構造・権限関係に対して発見能力を確認する。
- **Stage 3: 推論・再計画の追加価値を検証。** 公平な比較と必要な要素除去実験によって、どの条件で自律的な研究判断が追加発見に寄与したかを示す。
  改善がなかった場合も、その結果と適用限界を報告する。
- **Stage 4: 複雑性を広げる。** 複数機能・認証ロール・データオブジェクト・仕様の曖昧さを含む隔離案件へ段階的に広げる。
- **Stage 5: 実運用適性を評価する。** 明確な許可条件の下で、スコープ遵守・監査可能性・再現性・費用・運用上の制約を評価する。
  実在する外部プログラムでの実行は、別途明示的に判断する。

## 9. これまでの不具合から守ること（恒久）

1. **取得から出力まで追跡する**: 取得→判定→保存→再開→CLI/GUI→レポート→採点。通常経路・自律経路・labへの伝達漏れに注意する。
2. **主応答だけでなく根拠一式を見る**: 対照・追加確認・保存失敗・保存OFF・不完全本文を含める。
3. **旧データを正常と推定しない**: 新フィールドの欠落を完全・成功と解釈しない。契約変更時は版と再開互換性を検証する。
4. **説明文も機密情報の出力経路として扱う**: errors・URL・理由・候補・ログ・レポートまで、ダミー秘密値で非漏えいを確認する。
5. **テストPASSだけで能力を主張しない**: モック試験・実LLM評価・未知ケース評価・実環境検証を区別する。
6. **テストを弱めて数値を合わせない**: 正当な契約変更で期待値を変える場合は理由を説明し、旧予算・失敗ケースの回帰を残す。対照条件を緩めたり、未判定を成功に変えたりしない。
7. **評価定義と探索性能を混同しない**: 旧新の数値差を、定義変更・選択順・実行コスト・証拠不足に分ける。根拠なく係数調整を繰り返さない。
8. **文書の現在状態を一意にする**: 要求仕様・設計・実装計画・評価履歴の役割を分ける。過去の結果は保存し、古い記述を現在状態と混在させない。

## 10. 最優先事項

自律的な仮説形成・実験設計・再計画による脆弱性発見能力を実現し、その効果と限界を客観的に実証すること。
進捗は「自律型エージェント」という名称や部品数ではなく、**人間が用意していた研究判断をどこまでシステムが担い、その判断が実際の観測・発見につながったか**で報告する。
