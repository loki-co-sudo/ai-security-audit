> （変更 → `tools/run_selftest.py` → 修正）に従う。実装が済んだ項目は本書のチェックボックスと

## 1. 背景・想定ユースケース

これまでの開発でツールは「4モード・GUI・検出のみ・マルチモデルルーティング・バグバウンティ拡張」まで
到達している。次の段階は、単発のデモではなく**継続的に運用するツール**として成立させること。

想定する運用シーンは以下の3つ（いずれも既存の安全境界の内側で成立する）。ポートフォリオとしての
見栄えの向上は本ロードマップの目的ではない。

| シーン | 具体 |
|---|---|
| バグバウンティ実戦 | 許可されたプログラムへの実地調査。複数対象・情報源の広さ・報奨が出やすい脆弱性クラス・レート制限順守・提出しやすいレポート |
| 診断案件 / 内部レッドチーム | エンゲージメント単位の作業。スクリプト実行・所見の継続追跡（リテスト）・証拠（request/response）の保全・案件別設定・報告書 |
| 自インフラの継続モニタリング | 自分の資産を定期スキャンして変化を追う。永続台帳・前回差分・スケジュール実行・通知 |

## 2. 現状の構造的ギャップ

3つの運用シーンに共通して効いているボトルネックは3点。

1. **GUI専用** — `CustomTkinter` がアーキテクチャの土台で、CLI/ヘッドレス実行がない。cron・CI・
   SSH越し・複数対象の一括処理ができない。`tools/run_selftest.py` は既に GUI なしで `EventBus` 経由
   でエージェントを完走させており（`EventBus` は `queue.Queue` ベースで tkinter 非依存）、
   ヘッドレス実行の技術的な土台自体は存在する。
2. **状態を持たない** — レポートは毎回 HTML/PDF/MD の単発出力。スキャン履歴・前回との差分・
   誤検知の永続抑制・対応状況の追跡がない。「露出管理」の管理レイヤーが実在しない。
3. **検出品質を繰り返し測れない** — 最後の実測は 2026-08-17 の実LLM試運転。変更が精度に効いたか
   を再現可能な形で確認する手段がない（DEFENSE MODE の MITRE タグ付け精度問題を「盲目的な
   プロンプトチューニングになる」として見送った理由もこれ。[../AGENTS.md](../AGENTS.md) §4 参照）。

## 3. フェーズ別ロードマップ

各項目は「新設定・新トグルが未設定/OFF のとき既存挙動と完全に一致する」ことをテストで固定する
（[../AGENTS.md](../AGENTS.md) §3 の再発防止ルール）。ネットワーク・LLM を要さないテストは
`SELFTEST_NON_LLM_ONLY=1` でも回せるようにする。

### フェーズ1 — 足回り（3シーン全てが要求）

#### 1.1 ヘッドレス CLI / バッチ実行

- **目的**: GUI なしでスキャンを実行し、結果を機械可読な形で得る。cron・CI・リモート・
  パイプライン・複数対象の自動処理を可能にする。
- **実装の要点**:
  - 新規 `cli.py`（エントリポイント）。`EventBus` はそのまま流用し、GUI パネルの代わりに
    コンソール出力・JSON 出力を行う consumer を実装する。`tools/run_selftest.py` の
    EventBus ドレイン処理が参考になる。
  - 引数: `--mode {audit,attack,fuzz,defense}` `--target` `--targets-file`
    `--effort {speed,balanced,quality,auto}` `--format {text,json,md}` `--out <path>`
    `--profile <name>`（1.3）。
  - 終了コード: 検出ありなら非0（CI で失敗扱いにできる）。エラーは別のコード。
  - 設定は既存の `core/config.py`（`config.json`）をそのまま使う。CLI 引数が指定された
    項目のみ一時上書きする（`config.json` は書き換えない）。
- **対象ファイル（想定）**: `cli.py`（新規）、`core/event_bus.py`（consumer 追加の可能性）、
  各 `agents/*.py` は変更しない想定。
- **後方互換**: GUI（`main.py`）の挙動は不変。
- **テスト**: `tools/run_selftest.py` に、`cli.py` を各モードでサブプロセス起動し
  終了コード・JSON スキーマを検証する項目を追加（対象はローカル testlab サーバ・モック）。

#### 1.2 所見台帳（追記式 JSON Lines）+ 差分

- **目的**: スキャン結果を継続的に蓄積し、前回との差分を取れるようにする。誤検知を
  一度判定したら次回以降は自動で抑制する。
- **実装の要点**:
  - `reports/findings.jsonl` に1所見1行で追記（`reports/telemetry.jsonl` と同じ方式）。
    フィールド案: `ts, scan_id, mode, target, vuln_class, signature, severity, evidence,
    status, first_seen, last_seen`。`signature` は所見の同一性判定キー
    （target + vuln_class + 正規化した位置情報のハッシュ等）。
  - `cli.py diff --target <t>`（または直近2スキャン）で NEW / RESOLVED / REGRESSED を出力。
  - `cli.py suppress <signature>` で `status=suppressed` を記録。以後のスキャン結果表示・
    レポートから除外するが、台帳には残す（サイレントに消さない方針と整合）。
  - `cli.py status <signature> <open|fixed|accepted-risk>` で対応状況を更新。
  - **SQLite は採用しない**（v1）。追記式ファイルで運用上の不足（クエリ性能・整合性）が
    顕在化してから改めて検討する。telemetry 台帳が JSON Lines で始まった経緯と同じ判断。
- **対象ファイル（想定）**: `core/findings_ledger.py`（新規・純粋関数中心）、
  `cli.py`、`tools/report_generator.py`（抑制済み所見の除外フィルタ）。
- **後方互換**: 台帳ファイルが存在しない/空なら全所見が NEW 扱い。GUI からは当面参照しない
  （CLI 専用機能として始める）。
- **テスト**: 台帳の追記・signature 一致・diff 分類・suppress フィルタを非LLMで検証。

#### 1.3 エンゲージメント別プロファイル

- **目的**: 対象範囲・レート・エフォート等の設定一式を、プログラム/顧客ごとに切り替える。
- **実装の要点**:
  - `config.json` に `profiles: { <name>: { allowed_targets, scope_mode, scan_profile,
    effort, rate_limit, targets } }` を追加。既存のトップレベル設定は「デフォルトプロファイル」
    として維持する。
  - CLI `--profile <name>` で選択。GUI 側は将来対応（まずは CLI）。
  - CIDR・crt.sh 由来のサブドメインを対象に含める場合、**展開してよいホストをユーザーが
    明示的に指定**してからでないと後続フェーズに渡さない（blast radius 対策。
    [BOUNTY_ROADMAP.md](BOUNTY_ROADMAP.md) Phase B の「自動展開しない」方針を CLI にも適用）。
- **対象ファイル（想定）**: `core/config.py`（プロファイル解決ロジック・バリデータ）、`cli.py`。
- **後方互換**: `profiles` キーが無ければ従来のトップレベル設定のみで動作。
- **テスト**: プロファイル解決の優先順位（CLI 引数 > プロファイル > デフォルト）を非LLMで検証。

### フェーズ2 — 検出の信頼性と網羅

#### 2.1 ベンチマークハーネス（フェーズ2の最初に実施）

- **目的**: 既知の脆弱アプリに対する検出率（precision / recall）を1コマンドで数値化し、
  以後の変更が精度に効いたかを再現可能に判定できるようにする。
- **実装の要点**:
  - `testlab/` の脆弱サーバを拡張し、脆弱性クラスごとに「検出されるべき所見」の
    正解ラベル（ground truth）を YAML 等で持つ。
  - 任意で OWASP Juice Shop / DVWA / WebGoat（ローカル Docker）を対象に含められるようにする
    （デフォルトは testlab のみ。外部アプリは opt-in）。
  - `tools/benchmark.py`（新規）が CLI（1.1）でスキャンを実行し、所見を正解ラベルと突き合わせて
    per-class の TP / FP / FN と precision / recall を表に出す。結果は `reports/benchmark/` に保存。
  - DEFENSE MODE の MITRE ATT&CK タグ付け精度も、正解タグを持つサンプルログに対する
    一致率としてこのハーネスで測る（見送っていた検証をここで回収する）。
- **対象ファイル（想定）**: `tools/benchmark.py`（新規）、`testlab/`（正解ラベル追加）。
- **注意**: 実LLM・課金が発生するため CI では回さない。手動実行のツールとして位置づける。
- **順序**: 2.2 の網羅拡張より**先に**入れる。現状のクラスがどの程度堅いかを数値で把握して
  から新クラスを足す（勘で足さない。[../AGENTS.md](../AGENTS.md) の「明確に改善と言えるもののみ」
  という既存方針と整合）。

#### 2.2 WEB FUZZ 高価値クラスの拡張

- **目的**: バグバウンティで報奨が出やすく、診断案件でも定番の脆弱性クラスを検出対象に加える。
- **候補**（2.1 の数値を見て1〜2クラスずつ着手）:
  - SSRF（Server-Side Request Forgery）— 検出用の一意コールバックURLへの到達観測。
    外部リスナーを要するため、まずローカル testlab での検証に留める設計を検討。
  - オープンリダイレクト — リダイレクト先パラメータへの外部ドメイン注入と `Location` 観測。
  - CORS 設定不備 — `Origin` を変えたリクエストで `Access-Control-Allow-Origin` の
    反射・`*` + credentials を観測。
  - レスポンス / リンクされた JS 内のシークレット露出 — APIキー・トークンのパターン検出。
  - サブドメインテイクオーバー — 未使用の CNAME 先サービスの指紋を照合（**検出のみ**。
    実際の乗っ取り操作は行わない）。
  - GraphQL introspection の有効化検出。
- **安全境界**: すべて「兆候の観測」に留める。データ窃取・認証回避・RCE 実行・書き込み系
  リクエストは実装しない（既存の WEB FUZZ 不変条件を変えない）。総リクエスト数上限・
  同一オリジン限定・ジッター/低並列も維持する。
- **対象ファイル（想定）**: `tools/web_fuzzer.py`（検出ロジック）、`agents/fuzz_agent.py`
  （プローブ生成カテゴリ・トリアージへのエビデンス追加）。
- **テスト**: 2.1 のハーネスに各クラスの正解ラベル付きエンドポイントを追加。

#### 2.3 証拠バンドル + レート適応

- **目的**: 報告・提出の再現性を上げ、対象インフラへの負荷に配慮する。
- **実装の要点**:
  - 所見ごとに、その所見の根拠となった request / response ペアを保存する
    （`reports/evidence/<scan_id>/`）。レポート（MD/HTML）から参照できるようにする。
    保存対象は所見に紐づくもののみ（全通信のフルキャプチャはしない＝容量・秘匿情報の観点）。
  - HTTP 429 / `Retry-After` を尊重してバックオフする。連続 429 でスキャンを一時停止する。
  - プログラム別のレート上限を 1.3 のプロファイル（`rate_limit`）から読み、
    `SCAN_PROFILES["bounty"]` のジッター/並列度に反映する
    （[BOUNTY_ROADMAP.md](BOUNTY_ROADMAP.md) §7 の「将来検討」を回収）。
- **対象ファイル（想定）**: `tools/web_prober.py` / `tools/web_fuzzer.py`（429 ハンドリング・
  証拠保存フック）、`tools/report_generator.py`（証拠へのリンク）、`core/settings.py`
  （レート値のプロファイル連動）。
- **後方互換**: 証拠保存は既定 ON でも所見数に比例した容量しか使わない。プロファイルに
  `rate_limit` が無ければ従来の `SCAN_PROFILES` 値のまま。

### フェーズ3 — モニタリング仕上げ

#### 3.1 DEFENSE MODE の実ログ対応

- **目的**: サンプルログ生成前提から、実環境のログソースを直接監視できるようにする。
- **実装の要点**: journald（`journalctl -f` のパイプ）・syslog・JSON Lines 形式の
  アクセスログを入力に取れるようにする。構造化ログはフィールド（メソッド・パス・
  ステータス・UA・送信元IP）をパースして LLM プロンプトに渡す。
- **対象ファイル（想定）**: `tools/log_watcher.py`（入力ソースの抽象化）、
  `agents/monitor_agent.py`（構造化フィールドの活用）。
- **後方互換**: 従来のファイルパス指定・サンプルログ生成は残す。

#### 3.2 Slack / Webhook アラート出力

- **目的**: DEFENSE MODE のアラートを外部通知に流す（無人運用）。
- **実装の要点**: `config.json` に `alert_webhook_url`（空なら無効）。CRITICAL/HIGH の
  ALERT イベントを整形して POST する。送信失敗はサイレントに握りつぶし本処理を止めない
  （`tools/cve_client.py` のサイレント失敗方針を踏襲）。**スキャン結果本体の外部送信では
  なくアラート通知**である点を明確にする（「ローカル保存のみ」の不変条件に抵触しない
  設計にする — 送るのは深刻度と要約であって所見の生データではない、等の線引きを実装時に確定）。
- **対象ファイル（想定）**: `core/alert_sink.py`（新規）、`agents/monitor_agent.py`。

#### 3.3 チェックポイント / 再開

- **目的**: 対象リスト（1.3）で長時間化したスキャンが中断しても途中から再開できる。
- **実装の要点**: スキャンの進行状態（完了ホスト・完了フェーズ）を `reports/checkpoint/`
  に定期保存。`cli.py --resume <scan_id>` で未完了分から続行。
- **対象ファイル（想定）**: `cli.py`、各エージェントの run() にフェーズ境界の記録フック。

### 別枠（大きい・本ロードマップのスコープ外）

- **CODE AUDIT のポリグロット化（JS/TS 等）** — 現状の AST 前処理（`agents/audit_agent.py`）は
  Python の `ast` モジュール依存。他言語は別パーサ（tree-sitter 等）＝新規依存で、規模が大きい。
  独立したプロジェクトとして別途計画する。
- **HackerOne / Bugcrowd プラットフォーム API 連携（重複報告チェック等）** —
  [BOUNTY_ROADMAP.md](BOUNTY_ROADMAP.md) §7 の通り意図的に対象外のまま。

## 4. 優先順位の理由

- **フェーズ1 が最優先**: 3つの運用シーン全てが CLI・所見追跡・案件別設定を要求する。
  かつ CLI は既存の `run_selftest.py` が実行パスを実証済みで、エージェント本体を変更せずに
  追加できるため低リスク。
- **フェーズ2 は 2.1 → 2.2 の順**: 網羅を増やす前に、現状の検出品質を数値で把握する。
- **フェーズ3 はモニタリング用途に閉じる**: バグバウンティ/診断案件にはフェーズ1〜2で足りる。

---

## 5. 触ってはいけない不変条件（セキュリティ）

本ロードマップのどの項目も、[../AGENTS.md](../AGENTS.md) §3 の安全境界を変更しない。

- 検出のみ（データ窃取・RCE 実行・認証回避・書き込み系リクエストによる横断確認は非実装）
- PoC はローカル生成のみ・対象へ送信しない
- 非 DoS（総リクエスト数上限・ジッター/低並列）
- WEB FUZZ は同一オリジン限定
- スキャン結果はローカル保存のみ（3.2 のアラート通知は「所見の生データ送信」ではなく
  「深刻度・要約の通知」に限定して設計する）

新トグル・新設定は、未設定/OFF のとき既存挙動と完全に一致することをテストで固定する。

## 6. 検証

各項目の実装後は必ず:

```bash
.venv/bin/python3 tools/run_selftest.py
```

を実行し、既存項目の回帰がないこと・追加テストが PASS することを確認する。
新規テストは可能な限り非LLM・非ネットワーク（モック・ローカル testlab）にし、
`SELFTEST_NON_LLM_ONLY=1` でも回せるようにする。

フェーズ2.1 のベンチマークハーネスは実LLM・課金が発生するため CI 対象外。
重要な変更の前後で手動実行し、精度の数値を比較する。

```

条件:
- 未着手（- [ ]）の項目から、依存関係とフェーズ順を尊重して選ぶ
- 選んだ項目について、実装計画（対象ファイル・関数レベルの変更点・後方互換の担保方法・
  追加するセルフテスト項目）を具体化する
- AGENTS.md §3 の安全境界と「OFF時は既存挙動と完全一致」ルールを守る前提で

  advisor にかける。advisor の指摘は重く扱い、実測やソースと矛盾する場合だけ再相談で解消する。
  advisor が使えない場合は現セッションで同等の自己批判レビューを行い、その旨を明記する
```
